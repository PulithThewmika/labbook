# Running LabBook on OpenChoreo

[OpenChoreo](https://openchoreo.dev) is the open-source internal developer platform that Choreo is built on (Apache-2.0). It runs on a local Kubernetes cluster, so it needs no cloud account. This guide deploys the whole LabBook project to it: a PostgreSQL resource, the API, the web app and the scheduled task. It was run end to end on OpenChoreo v1.3.3.

The Choreo cloud runbook is in [deployment-choreo.md](deployment-choreo.md). Differences between the two are listed at the end.

## What you need

- Docker Desktop (Docker 26 or newer) with about 8 GB RAM and 4 CPUs available. Builds need that much.
- Ports 8080, 19080 and 19443 free.
- About 10 minutes for the first install and 10 to 15 minutes for the first builds.

## 1. Install OpenChoreo

Start the quick-start container (this is the documented command; keep the default entrypoint):

```bash
docker run --rm -it --name openchoreo-quick-start --pull always \
  -v /var/run/docker.sock:/var/run/docker.sock --network=host \
  ghcr.io/openchoreo/quick-start:v1.3.3
```

Inside the container, install with builds enabled:

```bash
./install.sh --version v1.3.3 --with-build
```

The installer creates a k3d cluster, installs OpenChoreo with Helm, and prints the portal address (`http://openchoreo.localhost:8080/`) and the default local logins. Run `./check-status.sh` to confirm every plane reports `READY`.

Scripting note: if you drive the container with `docker exec` instead of an interactive shell, add `-u openchoreo` (the installer refuses to run as root), and do not override the image entrypoint (it sets up Docker socket access).

## 2. Deploy LabBook

From a checkout of this repository (copy `deploy/` and `db/` into the container, or clone the repo there):

```bash
bash deploy/openchoreo/apply.sh
```

To build another branch instead of `main`, set `LABBOOK_BRANCH`:

```bash
LABBOOK_BRANCH=my-branch bash deploy/openchoreo/apply.sh
```

The script:

1. Creates the `labbook` project with development, staging and production bindings (`deploy/openchoreo/project.yaml`).
2. Creates a `postgres` Resource. The schema and demo data come from `db/migrations/*.sql`, run once at first start as the database superuser. The app user and its password are generated by OpenChoreo.
3. Creates three Components (`deploy/openchoreo/components.yaml`) and starts their builds from this GitHub repository.
4. Sets the scheduler to run every 15 minutes.

Watch it with `kubectl get workflowruns,components -n default`. When a build succeeds, OpenChoreo deploys it to the development environment automatically.

| Component | Type | Built from | How |
|---|---|---|---|
| `labbook-api` | service | `backend/` | `backend/Dockerfile` |
| `labbook-web` | web-application | `frontend/` | `frontend/Dockerfile` (Node build, then nginx) |
| `labbook-scheduler` | scheduled task | `scheduler/` | `scheduler/Dockerfile` |

Each directory also has a `workload.yaml` that declares its endpoints, environment variables and dependencies. The database connection reaches the API and scheduler through the Resource's outputs, mapped to Ballerina's `BAL_CONFIG_VAR_*` variables.

## 3. Open the app

Find the web hostname and open it on port 19080:

```bash
kubectl get httproute -A
```

Use the `web-labbook-web-development-...openchoreoapis.localhost` entry, for example `http://web-labbook-web-development-default-<hash>.openchoreoapis.localhost:19080`. The first API start takes up to two minutes (JVM start under the pod's CPU limits); until then `/api/*` returns 502.

nginx in the web pod proxies `/api/` to the API component, so the browser uses a single origin and the SPA needs no CORS settings.

## 4. Verify

```bash
U=http://web-labbook-web-development-default-<hash>.openchoreoapis.localhost:19080
curl "$U/api/health"                                    # {"status":"ok"}
curl -H "X-Dev-User: admin@labbook.dev" "$U/api/me"     # role: admin
```

Book the same lab slot twice as two different users: the first call returns 201 and the second returns 409 `BOOKING_CONFLICT`, enforced by the database constraint inside the cluster. Run the scheduler once by hand:

```bash
kubectl create job -n <dp-namespace> labbook-scheduler-manual --from=cronjob/<labbook-scheduler-cronjob>
kubectl logs -n <dp-namespace> job/labbook-scheduler-manual     # expired=0 completed=0
```

## Authentication in this setup

This local deployment runs the API in dev mode (`X-Dev-User` header, with a Student/Admin picker in the SPA). It is for a demo on your own machine only. OpenChoreo ships an OIDC identity provider (ThunderID), so real sign-in is possible, but it is not wired into LabBook yet. Do not expose this deployment to a network.

## Findings worth knowing

- **Ballerina buildpack and Java.** OpenChoreo's `ballerina-buildpack-builder` installs a Java 21 runtime, and Ballerina 2201.14.x needs Java 25 (`UnsupportedClassVersionError ... class file version 69.0`). The buildpack ignores `BP_JVM_VERSION`. This project builds with Dockerfiles on the official `ballerina/ballerina:2201.14.2` image instead (user `ballerina`, group `troupe`).
- **App URL.** The deploy scripts print the real hostname, which includes a hash. The hostname in some docs without the hash returned 404.
- **Scheduled task schedule.** The cron expression is an environment config on the ReleaseBinding (`componentTypeEnvironmentConfigs.schedule`, default `1 * * * *`), not a Component parameter.
- **Build order.** The web component can deploy before the API exists; its `LABBOOK_API_URL` still resolves because the address is derived from the component name.

## Differences from Choreo cloud

| Topic | Choreo cloud | OpenChoreo (local) |
|---|---|---|
| Component config | `.choreo/component.yaml` | `workload.yaml` plus Component manifests |
| Build | Buildpacks or Dockerfile in the console | `ClusterWorkflow` (`dockerfile-builder`, buildpack builders) |
| Login | Managed Authentication with Asgardeo | ThunderID (not wired in); dev mode here |
| API gateway JWT | `X-JWT-Assertion` header | Not used in this setup |
| Database | Managed database or Neon | `postgres` Resource, in-cluster, PVC-backed |
| Observability | Built into the console | Optional plane (`--with-observability`), not installed here |

## Clean up

```bash
./uninstall.sh                     # inside the quick-start container: removes the cluster and everything in it
docker rm -f openchoreo-quick-start
```
