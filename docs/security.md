# Security

## Trust chain

1. The browser is redirected to ThunderID, OpenChoreo's identity provider, and signs in there. LabBook never sees the password.
2. LabBook is a public OIDC client: it uses the authorization code flow with PKCE (S256), so no client secret is stored in the browser. The code exchange goes through the web app's own nginx (`/idp/token`), which forwards it to ThunderID inside the cluster.
3. The SPA sends the access token to the API as `Authorization: Bearer <jwt>`.
4. `labbook-api` verifies the token before trusting any claim.

## Why the signature is verified

Anyone who can reach the API could send a made-up header or token. Decoding a JWT only reads it; verifying the signature against the issuer's keys (`jwtIssuer`, `jwtJwksUrl`) proves ThunderID issued it. `auth.bal` uses `ballerina/jwt` for this and answers `401 UNAUTHENTICATED` otherwise. The issuer is checked too.

## Roles

`sub`, `email` and the name claims come from the verified token. A user gets `role = 'admin'` when their email is in the `adminEmails` configuration, otherwise `student`. The role is re-evaluated on every call, so removing an email takes effect immediately. Admin-only routes return `403 FORBIDDEN` to students.

## Dev mode

With `devMode = true` the API accepts `X-Dev-User: <email>` instead of a token and logs a loud warning at startup. The default is `false`, and the OpenChoreo manifests set it to `false`. **Never enable `devMode` on a shared or public deployment**: anyone could then impersonate any user, including an admin. It exists so the app can run locally without an identity provider.

## Secrets

- The database password is generated by OpenChoreo's Postgres resource and bound to the components at deploy time. Nothing secret is committed: `Config.toml`, `.env*` and `*.local` are gitignored, and only `*.example` files are in git. The files under `tests/` use the throwaway local development password.
- The ThunderID client is public and has no secret. Registering it uses the installer's system credential, which `register-thunder-app.sh` reads at run time and never prints.
- Logs contain no tokens or personal data, only method, path, status and duration.

## Known limits of this setup

- The access token is kept in `sessionStorage`. That is fine for a local demo; a production setup would use a backend-for-frontend or short-lived tokens with refresh.
- ThunderID and the apps run over plain HTTP on `localhost`. Use TLS anywhere beyond your own machine.
- The token audience is not checked yet; issuer and signature are.

## SQL injection

All queries use Ballerina `sql:ParameterizedQuery` with bound values. Strings are never concatenated into SQL.

## Data integrity

Double bookings are prevented by database exclusion constraints, not only by application checks. Error responses never include SQL text or stack traces.

## Future work

Rate limiting, an audit log of admin decisions, audience checks, token refresh, and email notifications are out of scope for v1.
